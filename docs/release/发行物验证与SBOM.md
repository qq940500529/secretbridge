# 发行物验证与 SBOM

[文档中心](../README.md) / 发行物验证与 SBOM

SecretBridge 原生包同时携带程序、Web 资源、对应源码、许可正文、文件清单和机器可读的软件物料清单。校验目标是让使用者在安装前发现损坏、混装或元数据不一致，而不是把一个未签名文件描述成已经获得发行者身份背书。

## 包内材料

| 文件 | 用途 |
| :--- | :--- |
| `secretbridge-package.json` | 安装器允许的文件、长度和 SHA-256；固定平台、架构、版本与 schema |
| `SBOM.cdx.json` | CycloneDX 1.6 组件清单，覆盖当前目标解析到的 Cargo 组件和 Web 生产依赖 |
| `SOURCE.tar.gz` / `SOURCE.json` | 对应源码与基线提交、源码摘要、规范化时间和脏状态 |
| `THIRD_PARTY_LICENSES.txt` | 锁定依赖的许可正文及必要的固定上游来源 |
| `*.sha256` | 整个 ZIP 或 tar.gz 的下载后完整性摘要 |

SBOM 的根组件是 SecretBridge，记录版本、目标平台、架构和源码提交。组件使用稳定 `bom-ref` 和 purl；许可证字段来自锁定的 Cargo/npm 元数据。它是发行组件清单，不是漏洞结论、法律意见或运行时进程列表。

## 安装前离线校验

解压包后，优先使用已安装的可信版本或从可信位置取得的校验程序运行：

```console
secretbridge verify-package /absolute/path/to/unpacked-package
```

校验按以下顺序完成：

1. 只接受当前系统平台、架构和受支持 schema 的严格清单；
2. 拒绝绝对路径、父目录、平台转义、符号链接和未允许的文件类别；
3. 逐个核对长度和 SHA-256，并要求 Web 构建元数据与包版本一致；
4. 要求 CycloneDX 1.6 根组件版本、平台和架构与包清单一致；
5. 输出不包含安装路径中的文件内容、凭据或页面配对材料。

校验成功只读取包目录，不执行目录中的候选程序、不启动后台、不写安装记录、不访问凭据库。原生程序版本在构建包时核对，安装激活候选版本时再次核对。`install` 会重新执行包校验，不能用先前成功结果绕过安装时检查。首次安装尚无可信本地校验器时，外层摘要只能检查下载完整性；在平台签名完成前，它不能独立证明发行者身份。

## 确定性打包

正式打包以当前 Git 提交时间作为规范化时间；自动构建也可设置整数 `SOURCE_DATE_EPOCH`。源码 tar、发行 ZIP/tar.gz、文件顺序、所有者、权限和时间字段均由打包器固定。相同的源码树、Web 构建、原生程序、许可材料与目标信息应得到相同归档字节。

发布工作流对同一组已编译输入执行两次独立打包，并运行：

```console
python tools/release/verify_reproducible_packages.py dist/packages-a dist/packages-b
```

比较要求包名、完整归档 SHA-256 和两侧摘要文件全部一致。该检查证明**打包步骤**没有引入当前时间、临时路径或文件遍历顺序差异；由于两次打包复用同一个已编译程序，它不证明不同构建机重新编译产生的二进制已经逐字节一致。

## 篡改与失败处理

- 外层 `*.sha256` 适合发现下载损坏，但没有签名时不能证明摘要来自版权方；
- 内层清单会阻止单个文件替换，清单自身变化则产生不同的版本目录标识；
- SBOM 即使重新计算摘要，若根版本、平台或架构不一致仍会被拒绝；
- 激活前失败不会停止当前后台；激活后候选版本异常会恢复旧指针、启动项和上一版本。

不要手工修补安装包后继续分发。需要修改任何文件时，应从对应源码重新构建并产生新的完整归档、摘要、源码快照和 SBOM。

## 尚未覆盖

开源版当前采用未签名发行包，不把 Windows Authenticode、macOS Developer ID/公证或 Linux 软件源签名作为 1.0 发布条件。使用者应通过官方发布入口、外层 SHA-256、包内清单、对应源码和 `verify-package` 共同检查下载及内容完整性；这些机制不能替代发行者身份签名。原生包发布工作流会先执行[固定版本的依赖漏洞门槛](./依赖漏洞与发行门槛.md)，然后在三个目标平台执行许可证、SBOM、确定性打包和离线校验。
