# 依赖漏洞与发行门槛

[文档中心](README.md) / 依赖漏洞与发行门槛

SecretBridge 在普通 PR、`main` 更新和原生包发布前检查锁定的 Rust 依赖与 Web 生产依赖。该门槛用于发现公开漏洞并阻止未经评审的发行，不把一次扫描通过解释为“没有漏洞”，也不代替源码评审、运行时测试或安全报告流程。

## 检查范围

| 范围 | 扫描器 | 输入 | 结果来源 |
| :--- | :--- | :--- | :--- |
| Rust 工作区 | `cargo-audit 0.22.2` | `Cargo.lock` | RustSec Advisory Database |
| Web 生产依赖 | `pnpm 11.23.0 audit --prod --json` | `pnpm-lock.yaml` | 当前 npm 注册表公开安全公告接口 |

扫描器版本保存在 [`security/dependency-vulnerability-policy.json`](../security/dependency-vulnerability-policy.json)，并与根 `package.json` 的 pnpm 版本互相核对。CI 以精确版本安装 Rust 扫描器，不采用浮动的 `latest`；pnpm 由 Corepack 按仓库声明提供。扫描器、公告数据库和注册表都可能变化，因此相同锁文件在不同日期可能得到不同结果，这属于漏洞情报更新，不是构建不确定性。

本检查不扫描 Web 开发依赖，因为它们不进入原生发行包；开发工具仍受锁文件、许可检查、构建测试和依赖更新评审约束。Rust 的锁文件扫描覆盖工作区解析到的 crates，实际随各平台发行的组件继续以三平台 CycloneDX SBOM 为准。

## 本地执行

先安装仓库固定的扫描器版本，再运行统一入口：

```console
corepack enable
pnpm install --frozen-lockfile
cargo install cargo-audit --version 0.22.2 --locked
python tools/check_dependency_vulnerabilities.py
```

命令在公告源不可访问、扫描器版本不符、报告格式异常、发现未处置漏洞或例外失效时返回非零状态。它不会因注册表故障假装扫描成功，也不会输出依赖路径之外的本机环境信息。

## 结果与处置

| 结果 | 含义 | 处理方式 |
| :--- | :--- | :--- |
| 阻断 | 扫描器报告已知漏洞，且没有精确匹配的有效例外 | 优先升级、移除或替换依赖，重新运行全部回归 |
| 误报 | 已核对公告、受影响版本和实际使用方式，确认扫描结果不适用于本项目 | 记录 `false-positive` 例外、证据摘要和最长期限 |
| 接受项 | 暂无可用升级且已明确不可达范围、缓解措施与剩余风险 | 记录 `accepted-risk` 例外；到期前必须重新评审 |

例外必须同时精确匹配生态、公告编号和包名；必须说明影响范围与决定理由，记录评审和到期日期。单次有效期最多 90 天。已到期、重复、字段不完整或当前扫描已不再出现的例外都会使门槛失败，避免临时接受项长期沉积。例外只允许处置公开依赖公告，不能用于跳过测试失败、许可证问题、秘密泄漏或发行物校验错误。

例外结构如下；示例编号和包名仅用于说明格式：

```json
{
  "ecosystem": "cargo",
  "advisoryId": "RUSTSEC-2099-0001",
  "package": "example-crate",
  "decision": "accepted-risk",
  "scope": "Only an unused optional feature is affected in the locked package.",
  "reason": "No affected API is reachable; upgrade is tracked before expiry.",
  "reviewedOn": "2099-01-01",
  "expiresOn": "2099-03-01"
}
```

实际增加例外时，应在 PR 中链接上游公告和升级跟踪项，但不要把漏洞利用细节、真实凭据或业务系统信息写入公开仓库。

## 与发行物完整性的关系

漏洞门槛回答“锁定依赖是否存在当前已知且未处置的公开漏洞”。发行流水线还独立执行以下检查：

1. 锁定依赖许可证与第三方通知检查；
2. 三个平台各自生成 CycloneDX 1.6 SBOM；
3. 用同一编译输入独立打包两次并比较完整归档 SHA-256；
4. 对解包内容运行 `verify-package`，检查清单、文件摘要、Web 构建元数据、schema 和 SBOM 根元数据；
5. 执行隔离的安装、升级、回滚与卸载生命周期验收。

原生包当前不签名。用户须从官方仓库发行入口取得文件，并按[发行物验证与 SBOM](发行物验证与SBOM.md)核对外层摘要与包内清单；摘要和内部一致性检查不能单独证明发行者身份。
