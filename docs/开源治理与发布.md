## 依赖与资产准入

每个新增组件须提供准确版本、来源、许可、分发方式和维护理由。无许可证不等于可自由复制；第三方图片、图标、字体、示例、截图和文案也需要登记。

1. 引入前阅读具体版本的许可证原文及NOTICE，检查开源版兼容性和商业版可交付条件。
2. PR声明是否修改上游内容、是否静态／动态链接、是否随安装包交付。
3. 保留原文件版权，更新[第三方声明](../THIRD_PARTY_NOTICES.md)。
4. 锁定依赖并核验间接、平台和可选依赖；不要只看顶层包名。
5. 发行时将SBOM与安装包实际内容对照，补齐运行时和辅助文件。

当前应用依赖尚未引入，选型文档不等于发行依赖清单。对于来源、许可或权利链不明的材料，保持未批准状态。

<a name="section-3"></a>

## PR与仓库权限

main的目标保护要求是：通过PR修改、必需检查通过、讨论解决、不允许强推或删除。维护者应定期核对远端实际设置；文档不是平台配置的实时证明。

当前工作流在Windows、Linux、macOS运行仓库检查及检查器测试。CI采用只读内容权限，第三方Action固定完整提交SHA，checkout不持久保存凭据。普通PR不应接触生产秘密、发布签名或含业务资料的自托管runner。

应用实现后追加Rust／TypeScript构建与静态检查、漏洞与许可扫描、单元／集成／安全测试。依赖更新通过PR评审；不能因自动更新工具标注安全修复就跳过影响分析。

## 质量门槛

| 阶段 | 必需交付与证据 |
| :--- | :--- |
| 设计基础 | 中英文首页、架构、安全模型、许可、贡献规范、模板、有限仓库检查 |
| 应用原型 | 三平台构建、锁文件、接口与状态测试、合成数据演示 |
| 安全试点 | 身份隔离与攻击测试、输出泄漏测试、失败路径、高危问题关闭 |
| 产品候选 | 可访问性、原生平台验证、安装卸载、升级回滚、使用文档 |
| 正式发行 | 对应版本源码及许可材料、SBOM、校验值、签名／公证、兼容矩阵与已知问题 |

覆盖率、模拟测试和仓库徽章不能代替真实应用质量。安全敏感代码在稳定发行前需要独立复核；无法完成时应记录缺口，不宣称完成审计。

    A["冻结候选提交"] --> B["测试与安全评审"]
    B --> C["版权及依赖复核"]

<details>
<summary>发布检查清单</summary>

- [ ] 版本号、来源提交、支持平台和已知问题一致。
- [ ] 分别核对开源版与商业授权范围，未决权利问题已解决或排除。
- [ ] 对应源码、构建／安装材料及适用许可履约材料与二进制匹配。
- [ ] SBOM、第三方通知、校验值和签名随交付提供。
- [ ] 安装、升级、卸载、回滚及用户配置保留行为有实测记录。
- [ ] 发布凭据来自受保护环境，普通PR不可读取，发布需人工批准。
- [ ] 下载链接、源码入口、签名验证和变更记录经发布后复核。
- [ ] 应用“关于／许可证／此版本源码”入口可用；适用网络源码提供义务有实现。

</details>

当前仅维护设计与仓库工具，不发布应用版本或安装包。实际阶段见[路线图](../ROADMAP.md)。未来商业交付的支持承诺由协议决定，不继承未约定的SLA。

<a name="section-6"></a>

## 公开内容与事件响应

公开仓库只接收项目所需且可合法公开的材料。不得上传真实凭据、业务数据库、客户文件、终端转储、私人聊天、个人路径或其他项目的Git历史。检查完整待提交差异与历史，不只检查文件当前版本。

启用并定期核查GitHub可用的秘密扫描、推送保护和私人漏洞报告。仓库自带检查器只覆盖有限模式；后续应引入固定版本的成熟扫描器，不能将检查通过作为无泄漏保证。

若发生公开泄漏，先在源系统撤销或轮换凭据并控制访问，再清理副本及协同平台处理。删除最新文件或重写历史不能保证外部副本已消失。遵循[安全报告流程](../SECURITY.md)，不在公开Issue补贴原始秘密。
