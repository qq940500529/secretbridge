## 顶层按什么划分

顶层按产品源码责任划分：`frontend/` 是 Web 管理界面，`backend/` 是本机 Rust broker，包含 HTTP、MCP、执行器、终端及 CLI。Web 由 backend 在本机提供，不是独立公网服务。仓库根仍是 Cargo/pnpm 工作区和项目治理入口。**主程序直接位于 `backend/`**，没有 `backend/secretbridge/` 这类重复产品名目录。

```text
SecretBridge/
├─ frontend/                       # Vite/React 管理界面，原 web/
│  ├─ package.json
│  ├─ src/
│  │  ├─ app/                     # 启动、导航、配对页面状态
│  │  ├─ api/                     # 按资源拆分的请求与生成的 HTTP 类型
│  │  ├─ features/
│  │  │  ├─ auth/                ├─ catalog/
│  │  │  ├─ tasks/{templates,approvals,runs,shared}/
│  │  │  ├─ terminal/            ├─ history/
│  │  │  └─ settings/
│  │  └─ shared/ui/               # 有两个以上真实功能使用的控件
│  └─ {index.html,tsconfig.json,vite.config.ts}
├─ backend/                        # 主 Rust 包，Cargo 包/二进制均名 secretbridge
│  ├─ Cargo.toml
│  ├─ src/
│  │  ├─ {lib,main}.rs            # 薄入口
│  │  ├─ domain/                 # 纯业务规则
│  │  ├─ application/            # 用例与所需端口
│  │  ├─ adapters/
│  │  │  ├─ {http,mcp,native_ipc}/
│  │  │  ├─ {persistence,secrets,executors,terminal}/
│  │  ├─ runtime/                # 组合、启停、诊断
│  │  ├─ cli/                    # 安装、升级、回滚命令
│  │  └─ acceptance_tests/       # crate 内安全/稳定性场景
│  ├─ tests/                     # Rust 跨层/公开契约测试
│  └─ local-access/              # 内部辅助 Cargo 包：本机权限边界
│     ├─ Cargo.toml              # 包名 secretbridge-local-access
│     └─ src/{lib,windows,unix}.rs
├─ docs/                          # 入门、使用、安全、测试、开发、发行、治理、社区
├─ tests/                         # 仓库级契约、发行和验收测试
├─ tools/                         # 契约生成、检查、验收、发行脚本
├─ skills/secretbridge-operations/
├─ security/
├─ .github/
└─ Cargo/pnpm 清单与锁文件、README、许可证、贡献/安全等根文档
```

这里的 `backend/local-access/` 是后端内部**跨平台本机访问权限组件**，不是“Windows 版主程序”：Windows 的 ACL/命名管道安全描述符与 Unix 的文件/socket 权限分别放在平台实现文件中，向主程序提供窄接口。独立 Cargo 包仅用于隔离平台依赖与 Windows `unsafe` 审阅面；业务、密钥库、PTY 或各协议执行器不得借此塞入。需要注意它仍是工作区的辅助编译包，但**产品结构上从属于 backend**，不与 frontend/backend 平级。

## 当前三个 Rust 包如何处理

| 当前 | 目标 | 理由 |
|---|---|---|
| `crates/secretbridge-core/` | 并入 `backend/src/` 对应所有者 | 目前只有状态类型和版本常量、只供主包使用；`core` 名字大于实际责任。运行状态、HTTP DTO/API 版本、SQLite 版本分别归 application、HTTP、persistence。 |
| `crates/secretbridge-server/` | `backend/` | 不再有“前端/服务端之后又套一个产品名”；主程序不只是 HTTP server，Cargo 包与产物统一称 `secretbridge`。 |
| `crates/secretbridge-windows-pipe-acl/` | `backend/local-access/` | 现有包不仅处理 pipe，还处理文件和目录；和 Unix 权限逻辑放到同一个窄平台边界，以平台模块区分实现。 |

包名/二进制名的改变会影响安装路径、服务配置、发行包与外部 MCP `command`。本次只验证新版本的全新安装和自身生命周期，不提供旧版升级或旧数据库迁移；现有用户数据保持原样。磁盘 `synthetic_runs` 等历史命名可在新版本空库 schema 中直接更正，公开 `/api/v1/runs` 按新版本契约测试。

## 结构规则与交付

- `domain` 不依赖传输/数据库；`application` 编排用例并经明确端口访问外部能力；`adapters` 实现传输和外部系统；`runtime/composition.rs` 负责装配，不实现业务规则。
- 不保留新的 `catalog`、`helpers`、`tasks.ts`、`Workbench.tsx`、`project/` 等含混汇聚点。`shared` 需有实际复用，不因“未来可能”而创建。
- 各现有文件到目标文件的去向和拟新增文件，见[后端](./仓库结构规划-服务端迁移.md)、[前端/工具](./仓库结构规划-其他文件迁移.md)迁移表和[文档体系](./仓库结构规划-文档体系.md)。表是下一状态，不限制更晚新增文件。
- 内部导入、Cargo/pnpm 清单、CI、打包脚本、Skill 和文档链接一起更新；不留空壳。`target/`、`dist/`、`node_modules/`、本机数据和凭据不入库。
- 保持产品功能与必要安全边界；允许清理旧版专用的兼容代码和历史命名。按[验证方案](./仓库结构规划-验证方案.md)验收新版本的全新安装、运行和卸载，不把旧版迁移作为完成条件。
