# SecretBridge 仓库命名与边界审查

[结构总览](./仓库结构规划.md) · [逐文件迁移：后端](./仓库结构规划-服务端迁移.md) · [逐文件迁移：其他](./仓库结构规划-其他文件迁移.md) · [文档体系](./仓库结构规划-文档体系.md)

本审查针对当前 `codex/issue-133-architecture` 工作树（含尚未完成的本地草稿）。它只评价**名称与真实责任是否一致、边界是否可持续**，不是运行质量结论；本轮未实施业务代码改动。判断规则是：目录应表达稳定的所有权，文件名应能预示内容，独立包应有真实的构建/依赖/安全边界，持久化和公开协议的改名必须有正式迁移。

## 全仓审查结论

| 范围 | 现状证据 | 目标决定 | 性质 |
|---|---|---|---|
| 顶层与 Cargo 包 | 现有 `web/` 对 `crates/`，主包再嵌一层 `secretbridge-server/`；`core` 只有状态类型/常量；Windows 包作为顶层同级但也处理目录/文件 ACL | 顶层对称为 `frontend/`、`backend/`；主包直接在 `backend/`，名为 `secretbridge`；Windows 与 Unix 权限实现同归后端内部 `local-access/` 辅助包 | 层级、名称和安全边界一起调整 |
| Rust `catalog` | `catalog/mod.rs` 同放模型、策略、存储类型；`catalog/helpers.rs` 同放规则、SQL 查询、行转换和时钟 | 模型进 `domain`、策略编排进 `application`、SQL/行/迁移进 `adapters/persistence`；不保留 `helpers` | 所有权重定 |
| Rust `lib.rs`/`main.rs` | 根入口承载组装、路由或生命周期实现，远超入口职责 | 根只做显式导出和 CLI 转接；装配在 `runtime/composition.rs` | 拆分 |
| Rust `http_api`/`mcp` | `http_api/catalog_routes.rs` 混合多资源；`mcp/native_bridge.rs` 将本机 IPC 置于 MCP 下 | HTTP 以资源拆路由；MCP 只处理 MCP 工具；本机 IPC 独立 `adapters/native_ipc` | 改层级 |
| Rust `maintenance`/`runtime`/`lifecycle` | 相近名称散在多处，备份、配置、服务启停、安装命令边界不清 | 备份编排归 application，数据库操作归 persistence；后台启停归 runtime；安装/升级/回滚归 cli | 职责明确 |
| Rust `postgres.rs`/`postgres_run.rs`/`database_task.rs` | 一个是连接检查，一个是运行编排，一个是多数据库任务，文件名难预判 | 分别为 `executors/database/connection_check.rs`、`application/postgres_check.rs`、`executors/database/{postgres,mysql}.rs` | 语义重命名 |
| `SyntheticRun`/`synthetic_runs` | `/api/v1/runs` 的正式受控执行仍使用 `SyntheticRun` 名称与 `synthetic_runs` 表 | 内部统一为 `Run`/`CreateRun`/`CancelRun`；表名改 `runs` 必须走正式 schema 升级与旧备份恢复验证，不做仅改标识符的替换 | 明确数据迁移 |
| Web 根目录 | 页面、协议编辑器、测试、`App.tsx`、`api/client.ts`、`api/models.ts` 混在 `web/src`；后两者分别约 800/650 行 | `app`、按资源分的 `api`、按用户行为分的 `features`，HTTP DTO 从服务端契约生成 | 层级和单一事实源 |
| Web `features/shell` | 同含全局文案、状态胶囊、配对提示、终端加载视图 | 文案归 `app`；配对归 `features/auth`；终端加载归 `features/terminal`；真正通用的状态展示归 `shared/ui` | 不建新的“壳组件”桶 |
| Web `features/catalog/shared.tsx` | 同含目录文案、枚举标签、表单、列表、按钮与输入样式 | 目录共用布局单独文件；资源文案/标签归凭据或目标；按钮/字段仅在跨功能复用时入 `shared/ui` | 取消万能 `shared` 文件 |
| Web `Workbench.tsx` | 三个跨页面基础控件被一个抽象名聚合 | `shared/ui/{EditorDialog,MasterDetail,SectionTabs}.tsx` 及独立测试 | 按组件责任拆 |
| Web `features/tasks` | 原方案把模板、审批、运行及全部编辑器直接堆在 `tasks/` | 强制进入 `templates/`、`approvals/`、`runs/`；`shared/` 只留确实跨两种任务的规则 | 防止换名后的新大桶 |
| 文档 `project/` | 原方案把版本差异、贡献许可、Beta 反馈、社区待办混在一处；现有部署、安全、测试页面也有不同读者内容混写 | 产品版本差异与法律入口留 `docs/` 一级；按入门、使用、安全、测试、开发、发行、治理、社区归属；拆开混合页面 | 不建“项目资料”式伪分类 |
| 工具与测试 | 平铺脚本、测试名称侧重运行方式而非归属，CI/包脚本硬编码旧位置 | `checks/`、`contracts/`、`release/`、按浏览器/连接器/平台分的 `acceptance/`；测试与被测领域相邻；更新全部引用 | 调用路径完整迁移 |
| 根目录与 `.github` | README、许可证、Cargo/pnpm 清单、GitHub 工作流都是标准入口 | 保持原位；修改内链、构建命令和二进制路径，不为整齐而搬迁 | 保留准确位置 |
| Skill 与 `security/` | Skill 是独立分发契约；漏洞策略文件有明确专属用途 | 保持原位，更新示例和链接 | 保留准确位置 |

## 命名规则与迁移边界

- 名称首先反映**职责**，其次才反映技术：`server` 只适合纯服务进程，`core` 只适合真正多方共享且稳定的核心；`catalog`、`helpers`、`shell`、`shared`、`project` 不得作为无人认领代码的收容处。
- 不为单个文件机械新建目录；目录成立条件是清晰的读者/使用者、至少一个稳定聚合，以及可预测的新增文件去向。`shared` 必须有两个实际调用方，不能因“将来可能复用”而创建。
- Rust 的包边界与包内模块边界不同：目标的两个 Cargo 包都在 `backend/` 下，主程序直接位于 `backend/`，内部辅助包 `local-access/` 仅隔离本机目录/文件/IPC 权限。前端构建目录单列 `frontend/`，不在根目录摆一个 Windows 专属产品模块。
- 旧内部导入路径、测试名、脚本路径和文档链接一次性更新，不保留空壳。**外部可见**的可执行文件路径、安装记录、MCP 配置和磁盘格式另列升级/回滚测试；丢掉旧名称不能丢掉现有用户数据。
- `SyntheticRun` 的内部名可直接改；`synthetic_runs` 是持久化格式，目标若改名必须新增迁移版本、验证从当前版本升级及旧备份恢复，并在发行说明中明确。现有 HTTP `/api/v1/runs` 路径无需因为内部改名而改变。

这些结论已反映到[目标结构](./仓库结构规划.md)和迁移表；实现时发现新的命名冲突，按以上判据记录并修订计划，而不是为了满足预写的目录树强行归类。
